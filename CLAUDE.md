# Life — project notes

Personal life-tracking web app (React + TypeScript + Vite), built one feature module at a time. Mobile-first, local-first storage (IndexedDB) synced to Cloudflare D1 through a Worker, hash routing. Hosted on Cloudflare Workers behind Cloudflare Access.

## Workflow
- `main` is production: CI deploys the repo's default branch (`main`) on every push. Never push to `main` directly.
- Work on a feature branch from `main` and open a PR into `main`; the PR description says what changed, how it was tested, and whether it adds a D1 migration.
- Each same-repo PR gets a preview version (`preview` job in `ci.yml`): built with `VITE_PREVIEW_LABEL` (banner, client never pushes) and uploaded with `READ_ONLY=true` (the Worker rejects pushes). Previews read production D1 and never run migrations.
- Don't reintroduce `keep_vars` in `wrangler.jsonc`: preview versions carry `READ_ONLY=true`, and keeping vars could copy it into a production deploy.
- Before pushing: `npm test` and `npm run build` must pass.

- Upcoming work and ideas live in GitHub Issues (see `TODO.md` for labels and workflow); check them before starting a feature, reference the issue with `Closes #N` in the PR, and open new issues for follow-ups.

## Commands
- `npm run dev` — dev server
- `npm test` — vitest unit tests
- `npm run dev:full` — build + Worker + local D1 on :8787 (needs `.dev.vars`, copy from `.dev.vars.example`)
- `npm run build` — typecheck app and worker + Vite build (run before committing)
- `npm run deploy` — what CI runs: build, apply D1 migrations remotely, `wrangler deploy`

## Layout
- `src/App.tsx` — shell: header (name + sync dot + separator + page title, settings; plain, scrolls with the page), then the page for `#/calendar[/YYYY-MM | /YYYY-MM-DD]` (also `#/`), `#/stats[/<module>[/...]]`, `#/more`, `#/settings` or `#/<module>/...`. `lib/legacyRoutes.ts` redirects old links (`#/clothes/calendar`, `#/clothes/stats`, `#/work/...`)
- `src/nav.tsx` + `src/BottomNav.tsx` — the bottom bar belongs to the app, not to modules: Calendar · Closet · ＋ · Stats · More. The ＋ menu lists every module's `actions`; `hideNav` of a module hides the bar on its forms
- `src/CalendarPage.tsx` — the calendar is where modules meet: it renders the clothes month/day views and calls each module's `calendarLayer` hook (`CalendarLayer` in `modules/types.ts`: `mark(date)` on a day (dot / icon badge / labelled pill depending on zoom), `header(month)` in the sticky top, `daySection(date)` on the day screen). The month view (`clothes/CalendarView.tsx`) is a continuous, scrollable list of weeks like the iPhone calendar, with a continuous zoom: `--z` (0 compact dots, 1 photo + badge, 2 labelled pills) is set on `.cal` straight from the pinch (ctrl+wheel and the zoom buttons too) without re-rendering, every day renders all three looks and CSS cross-fades them and grows the row height, the pinched spot stays put, and on release it eases to the nearest level; pure helpers and tests in `calendarZoom.ts`. It scrolls inside its own box (`.cal-full` on `main`) and remembers zoom and scroll position. `src/StatsPage.tsx` does the same for stats: one tab per module with a `stats` entry. `src/Home.tsx` is the More tab (modules with `listed !== false`, plus Settings)
- `src/icons.tsx` — inline line icons; `public/` holds the PWA manifest and icons (`node scripts/make-icons.mjs` regenerates them)
- `src/lib/` — shared infrastructure
  - `db.ts` — IndexedDB wrapper; one object store per module (`STORES` + `DB_VERSION`). Every local write also queues an `outbox` entry
  - `sync.ts` — background sync: push outbox, then pull changes since a cursor. Last write wins per record
  - `useCollection.ts` — React hook that loads a store and exposes `save`/`remove`
  - `router.ts` — `useRoute`, `navigate`, `href`
  - `backup.ts` — JSON export/import covering every store
  - `image.ts`, `format.ts` — photo downscaling and background removal for item photos (`cutOutImage`: on-device `@imgly/background-removal`, lazy-loaded, model files from IMG.LY's CDN; pure clean-up in `cutout.ts`), money/date helpers (`money()` uses the display currency)
  - `settings.tsx` — synced app settings (single record in the `settings` store), e.g. display currency
- `worker/` — Cloudflare Worker: serves `dist/`, exposes `/api/sync/pull` and `/api/sync/push`, and verifies the Cloudflare Access JWT (`auth.ts`, fails closed). `protocol.ts` is shared with the client
  - `mcp.ts` + `mcpTools.ts` — MCP endpoint (`/mcp`, bypassed in Access, guarded by the `MCP_TOKEN` secret) so Claude can read the closet and log wears; `records.ts` holds the D1 upsert/list helpers. Tools must never edit existing records: wears go through the `inbox` store (below); new items/outfits have fresh ids so they're written directly
- `migrations/` — D1 schema. The server stores records as opaque JSON strings keyed by (store, id), so new modules need no server changes
- `src/modules/` — feature modules, registered in `src/modules/index.ts`
- `src/modules/clothes/` — first module; use it as the reference implementation
  - `importers/whering.ts` — pure Whering → ClothingItem/Outfit mapping (type-only imports so Node can run it), used by `scripts/import-whering.ts`
  - Closet list (Items | Outfits tabs on top, `ClosetTabs`): search bar + filter button; `FilterSheet` is the full-screen filter page (sub-category, colors, sort, status, favorites; category stays as tabs on the list) and `closetFilter.ts` holds the pure filter/sort logic
  - Outfits live in their own `outfits` store (`Outfit` in `types.ts`, helpers in `outfits.ts`); logging an outfit wear also logs each piece
  - Calendar (`#/calendar[/YYYY-MM | /YYYY-MM-DD]`, with the pickers under `#/clothes/calendar/YYYY-MM-DD/outfit|items|new-outfit`) is derived from dated `wears` only (`calendar.ts`); there's no separate calendar store
  - Closet review (`#/settings/closet-review[/<step>]`, linked from Settings → Closet): `ClosetReview.tsx` hub + per-step pages (season, occasion, category, color, pattern, material, style, fit) that bulk-edit item fields as chips; pure logic in `closetReview.ts` (not `review.ts`, which is the receipt review). Done stamps `item.reviewed[step]` so "Only new items" skips reviewed ones; `pattern`, `styles`, `fit` are fields added for it. The step pages hide the bottom bar (see `App.tsx`)
- Inbox: `inbox` store holds `WearRequest`s, `TagRequest`s, `OutfitEditRequest`s (rename, add/remove pieces) and `ItemEditRequest`s (field changes, never wears/photo/tags) and `PhotoRequest`s (`set_item_photo`: the Worker downloads the image; `processInbox` runs it through `preparePhotos` + `itemPhoto` (downscale, background removal when possible) before the app sets it on the existing item, then drops the image from the request) queued by the MCP endpoint. `processInbox()` (`clothes/inboxRunner.ts`, registered with `setAfterPull` in `main.tsx`, skipped in PR previews) applies them via pure `applyInbox()` after each pull, then marks them applied; wears are idempotent per date
- Receipts: Claude reads order emails via the Gmail connector and adds the clothes with the `add_receipt_items` MCP tool (`mcpTools.ts`; validation, item building and image download in `receipt.ts`). Items are fresh `ClothingItem`s with `needsReview: true` and ids `receipt-<message id>-<n>` (idempotent per email); the closet marks them (`ReviewMark`, banner, `reviewOnly` filter) and `ReviewFlow` (`#/clothes/review`, pure helpers in `review.ts`) is a bottom drawer over the closet that steps through them one at a time, each shown as the normal `ItemDetail` page in its `review` mode (every field editable in place; Save → `markReviewed()` and slide to the next; "Check later" keeps the flag and skips it for that visit; swiping the page left, handled with pointer events in `ReviewFlow`, is the same as Check later). When an item still needing review is shown (in the drawer, or on its plain item page), `useCutOutOnOpen` (`useCutOut.ts`) cuts out its photo's background on-device (`cutOutImage`, saved via pure `withCutOutPhoto()` only if the photo and item are still as they were; if the cut-out can't run, a photo over ~250k characters is just downscaled), and changing a photo on `ItemDetail` does the same (`itemPhoto` in `lib/image.ts`). Don't put `transform`/`will-change` on the sliding page: it would trap the fixed field sheets inside it (the swipe only sets an inline transform while dragging or settling). PR previews have Settings → "Add sample items to review" (`sampleReview.ts`), local only, since previews never push. MCP guards keep an item's wear history in one record: `add_item` and `add_receipt_items` refuse a same-name/brand duplicate of an active or stored item (`findDuplicate` in `receipt.ts`) unless the user confirmed, and `edit_item` only retires an item with `confirmRetire`; photos for existing items go through `set_item_photo`, and a receipt line added without an image gets a hint in the tool result to look for one in the other emails about the order. Other edit paths must keep `needsReview` (spread the record)
- `src/modules/work/` — office/home days, shown through `useWorkCalendarLayer` (badge on each calendar day, monthly target above the grid, a Work section on the day screen) and `WorkStatsRoute` (Stats → Work, tabs Overview / Trends / Times at `#/stats/work/<tab>`; pure stats in `insights.ts` and `work.ts`, charts from `clothes/charts.tsx`); no routes of its own. `workdays` store: days set by hand or imported from the employer's badge report (id = date, wins; status office/home/off/trip, optional `arrive`/`leave` you enter yourself on any day, `reason` for off days, `source: 'report'` on imported days, cleared on any hand edit). Settings → Import badge report runs `importers/badgeReport.ts` (pure: `parseBadgeReport` + `planImport`; never replaces days set by hand, except that a business trip in the report always wins, and drops the report's placeholder 08:00–16:00 on home days and trips); never commit the report; `workevents` store: arrive/leave/home check-ins the Shortcut sends to `POST /mcp/checkin` (`worker/checkin.ts`, own `CHECKIN_TOKEN` secret, under the `/mcp` Access bypass; see `docs/work-checkin.md`). Events are always fresh records, never edits. `work.ts` derives each day (`buildDays`), the monthly target (`workTarget` / `workTargetKind` / `workExtended` in the settings record; default: at most 7 home days a month, up to 10 with approval, flagged as "needs approval") and the stats
- `src/modules/checkins/` — Swarm (Foursquare) check-ins, read only, shown through `useCheckinsCalendarLayer` (pin badge on each calendar day, a Places section on the day screen); no routes of its own. `worker/swarm.ts` serves `/api/swarm/{status,connect,callback,sync,disconnect}` behind Access: OAuth code flow with `FOURSQUARE_CLIENT_ID` / `FOURSQUARE_CLIENT_SECRET` secrets, the access token lives in the D1 `integrations` table (never in `records`, which syncs to clients), and `sync` pulls `v2/users/self/checkins` newest first with `offset` (the API ignores `sort`/`afterTimestamp`: the first fetch walks the whole history, the client passing back the `offset`, then `integrations.history_done` is set and later fetches stop at the first check-in at or before the stored cursor) into the `checkins` store as immutable `swarm-<id>` records (batched; the client asks again while `more`). `SwarmSection` (Settings) connects/fetches and `startSwarmAutoSync` (main.tsx) fetches quietly on start, whenever the app returns to the foreground and every 5 minutes while open, if the last fetch is over 10 minutes old (`isDue`); both are off in PR previews. The Foursquare app's redirect URL must be `<origin>/api/swarm/callback`. Stats → Places (`PlacesStatsRoute`, tabs Overview / Trends at `#/stats/checkins/<tab>`; pure stats in `placeStats.ts`): top venues (tap one to see the outfits and pieces worn on the days you went, via `wearsByDay`), categories, cities, new vs repeat places, day streak, month/weekday/hour charts
- `src/modules/packing/` — trips in the `trips` store (`Trip` in `types.ts`). The checklist is derived by `packingList()` in `packing.ts` from planned outfits per day (`outfitPlan`) + hand-picked items + custom extras; only `packed` ids are stored. Clothes' calendar reads trips to mark trip days and offer "Log as worn" for planned outfits
- `src/modules/games/` — game nights (board/card games, individual play). Stores: `players` (roster), `gametitles` (`GameTitle`: name + `rule` high/low/manual) and `gamenights` (`GameNight` with its `matches`: players, `scores`, stored `winnerIds`, which default to `winnersFromScores()` but can be overridden). Games scored in rounds are `Match`es with `rounds` (points per round per player) and `live: true` while being played (`PlayGame`: scoreboard from pure `standings()` on top, a swipeable carousel of round cards (always editable, "Save changes" per card, a pill row shows which round, last card is the next round); `#/games/night/<id>/play/<matchId>`; `scores` = `roundTotals()`, finishing fixes `winnerIds`); live games are left out of the stats. Games whose name contains "domin" get a calculator icon beside each score field (`DominoPad`, keys 1–12 drawn as pips, tap to add up, Done fills the field; `domino.ts`). The player with the best points in a round (`roundWinners()`, by the game's rule) gets a yellow `.won` shade on that round's number (on a tie for the best points the user picks the winner: `Match.roundPicks`, chips on the round card) in the scoreboard and "Won by" on the round card. Pure stats in `games.ts` (records, streaks, head-to-head, per-game best score, plays per month). Routes `#/games` (Nights | Players | Games tabs), `/new`, `/night/<id>[/edit|/add|/match/<id>]`; calendar layer marks game nights (`useGamesLayer`), Stats → Games (`GamesStatsRoute`). Games whose name contains "waterdeep" record each player's Lord and their points before the Lord's bonus (`Match.waterdeep`, `waterdeep.ts`; `scores` stays the final total, so the bonus is the difference); Stats → Games lists per-Lord games, wins, average bonus and comebacks. With the Skullport toggle (`waterdeep.skullport`) a "value of each corruption" field appears on top and each player gets a count next to their name (`corruptionValue`, `corruptions`; older games stored a `corruption` list per player, still read by `playerCorruption()`), and Stats shows corruptions per game per player. The bottom bar scrolls sideways (`.tabs-scroll`, the ＋ stays pinned); add tabs in `nav.tsx`

- `src/modules/food/` — grocery receipts, listed under More (`#/food`, `#/food/receipt/<id>`). One `foodreceipts` record per receipt (`FoodReceipt` in `types.ts`: store, branch, date/time, printed total, `lines` with cleaned `name` + printed `rawName`, `kind` food/alcohol/deposit/bag/other, `quantity` + `unit` pc/kg/l, shelf `unitPrice`, `discount`, `paid` = quantity × unitPrice − discount). Receipts come from Claude through the `add_grocery_receipt` MCP tool (`mcpTools.ts`; untrusted input validated in `worker/groceries.ts`, which recomputes `paid` and warns when the printed total and the lines disagree); id = `food-<sourceId>` (the receipt's JIR or email id), so the same receipt is never added twice, and receipts are never edited from the tools. Deposits and bags stay in the data but out of food stats. Pure helpers and tests in `food.ts`. Planned (issue #107): products derived from lines, Open Food Facts photos/info, price comparison, inventory, shopping list

## Adding a module
1. Create `src/modules/<id>/` with `types.ts`, an `index.tsx` exporting a `LifeModule` (including bottom-bar `tabs`, ＋ menu `actions`, and `hideNav` for form routes), and its screens.
2. Add `'<id>'` to `STORES` in `src/lib/db.ts` **and bump `DB_VERSION`**, so existing users get the new store.
   Sync and backups pick the new store up automatically; the server needs no changes.
3. Register the module in `src/modules/index.ts`. Home, the nav and backups pick it up automatically.
4. Keep stats and other derived logic in pure functions (see `clothes/stats.ts`) with vitest tests next to them.

## Conventions
- Dates are stored as local `YYYY-MM-DD` strings (`today()` in `lib/format.ts`); timestamps as ISO strings.
- Never hard-delete history that stats depend on; prefer a status field (see clothes `status`).
- Use `wearCount(item)` for wear totals, never `item.wears.length`: imported items and outfits carry undated `priorWears`. Never invent wear dates.
- Forms must spread the existing record before overwriting fields they edit, so fields they don't show (tags, priorWears, occasions…) survive an edit.
- **Settings → Import items** upserts by `updatedAt` (newer wins); keep `updatedAt` current on every write.
- Never commit personal data exports (Whering exports, import files, backups).
- Add item (`#/clothes/new`) is a bottom drawer over the closet (`NewItem.tsx`, same `.review-sheet` look as the review drawer) showing the normal item page on a blank in-memory draft (`ItemDetail`'s `draft` prop: no wear history, a single Save at the bottom). The line at the top is the grip: drag it down to close. Nothing is stored until Save. Editing an existing item still goes through `ItemForm`.
- Prefer small icon buttons (≥ 44px touch target, with an `aria-label`) over text buttons for actions like add, remove, edit and toggle; keep text for primary Save/Cancel in forms.
- UI should look like the Whering app: icon buttons over text buttons (text only for primary Save/Cancel), floating menus (`IconMenu`, `.menu`) over drawers or inline button rows, flat-lay outfit tiles with floating round icon buttons (`.card-fab`), borderless photo grids (pieces float on the page, glass only on controls and the selected piece), and no cards inside cards — use flat sections and hairline lists instead of boxed rows.
- The look is Liquid Glass, with one rule: **glass is the control layer, content is flat.** Glass (translucent, blurred, rimmed; `--glass-*` / `--plate` tokens, last blocks of `src/styles.css`) is for what floats above the page: the bottom dock (a floating pill with a sliding lens, shrinks while scrolling down), ＋, buttons, search, chips/pills, segmented switches, tappable field values (`.field-pill`), menus and sheets (frosted panes), badges on photos, sticky action bars. Content never gets a plate, border or blur: the header (plain, scrolls away with the page), the item/outfit hero (the photo floats with a soft shadow), photo grids, `.card` sections (flat, hairline-separated), stat tiles, settings groups and lists. Don't add a boxed card for content; keep an opaque fallback for glass (`@supports`, `prefers-reduced-transparency`). The page background is plain `--bg`.
- There are no back buttons: swiping right goes back (`useSwipeBack` in `lib/useSwipeBack.ts`, wired in `App.tsx`; the destination comes from `parentRoute` in `lib/backRoute.ts`, so add new sub-pages there). It's skipped over inputs, sideways-scrolling rows, sheets and the filter page. Form Cancel buttons stay.
- Styling lives in `src/styles.css` with CSS variables on `:root` and a dark-mode override. Keep touch targets ≥ 44px and check layouts at 390px width.
